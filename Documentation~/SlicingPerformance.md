# 九宫格正确性与性能

## 渐变误切的原因和处理

旧实现只比较相邻行或列。在 Tolerate=2 时，每一步仅改变1个色阶的渐变，可以被当成一整段重复像素，累计差异并没有上限。直接查看切片 PNG 时构图本来就会变化，但这个误判还会导致 Unity 按 Border 还原后出现色带。

修复后使用整段每个位置的 RGBA 最小/最大值判断。容差0采用精确比较和遇到首个不匹配即停止；精确相等具有传递性，不需要维护整段范围。非零容差仍属于近似处理，照片与插画建议保持0，强制保留源图用源图层的 `@NoSlice` 标记。

验证夹具中的2560²插画，旧容差2输出1976×1922并出现色带；容差0输出2560×2560、Border为0，无压缩原生渲染与原图逐像素一致。原图及商业工程夹具不随包发布。

## 加速路径

1. C#：精确扫描早停，整行连续拷贝，未切片时不创建输出纹理。
2. 可选 Burst/Jobs：容差0且总像素不少于1,048,576时，支持可读RGB24、RGBA32、ARGB32、BGRA32。行列扫描和输出行复制分别调度，临时NativeArray均在Job完成后释放；源像素借用只读视图，不销毁或改写输入纹理。
3. Trigger：无需切片时直接保留原始文件字节，不再次编码；PNG读取尺寸走IHDR，不为尺寸信息额外创建整张纹理。

Burst为可选Editor程序集，没有安装或关闭编译时仍可导入。测试过不安装Burst的新工程。小图不会调度Jobs；非零容差继续使用有整段误差约束的C#算法。Burst内核采用同步首次编译以保证后续执行路径明确，首次编译可能阻塞当前导入；其成本受本地编译缓存影响，不保证每台机器相同。Unity的相关编译机制见[官方说明](https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/compilation-overview.html)。

## 实测口径

2026-11-05，Unity 6000.3.27f1、Windows、Burst1.8.31、11个Job工作线程。以下是同一Editor进程的热态3次中位数，比较完整 `Slicer.Slice`（不含PNG解码/编码）：

| 输入 | 原实现C# | 修复后C# | 自动Burst路径 |
| --- | ---: | ---: | ---: |
| 2560²插画/ARGB32 | 408.52ms | 68.14ms | 31.48ms |
| 小图/512² | 约7ms | 约3ms | 走C#后备 |
| 平色图/2048² | 130.29ms | 105.34ms | 20.39ms |

该插画的 `TrySlice` 无需输出纹理判定约5.47ms。完整Trigger（含SHA、图片解码与扫描）约182.49ms，直接保留原PNG。单独重新编码这张图约429.58ms，不能把它混在“切片扫描”中声称已由Burst加速。PNG/JPEG实际需要编码时，编码及AssetDatabase导入仍有各自成本。

首个1024²调用在本机已有缓存下约42ms；不代表清空缓存后或其他机器的冷启动成本。本轮Unity Mono分配计数API返回0，因此未将它用作“零GC”或总内存结论。

## 正确性检查

原生专项验证81项通过，覆盖RGB/alpha渐变、正常九宫格、严格模式与原算法一致、CPU/Burst四种像素格式一致、横向/纵向/双向切片、输入只读、真实插画、无需切片返回null及原始字节保留。

`Tests~/Editor` 提供12个不依赖商业资源的EditMode回归：四个渐变方向/通道组合、正常面板压缩、不变PNG原字节保留、四种像素格式CPU/Burst一致及PNG/JPEG尺寸读取。安装Burst的验证工程中12项全部通过；未安装时专用Burst比较会跳过，其余用例继续执行。
